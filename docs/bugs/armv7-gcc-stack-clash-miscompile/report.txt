Title
-----
[arm] [Ada] -Os -fstack-clash-protection keeps a local below the stack
pointer across a call in the GNAT binder's adainit (Thumb-2, GCC 15.2.0)

Status: not yet reported upstream.  Written up from a reproduction in the
ada-on-alpine overlay; see "Not yet established" before filing.


Summary
-------
On armv7 (arm-alpine-linux-musleabihf), GCC 15.2.0 compiles the GNAT
binder-generated `adainit` of the gprbuild executable with a local variable
stored at [r7, #-8], where r7 == sp.  That address is below the stack
pointer, outside the function's frame.  The function then calls
memcpy through the PLT and, after the call, reloads the local from the
same slot.  The musl dynamic linker's lazy-binding stub runs in between and
overwrites that memory, so the reloaded value is garbage.

The garbage is stored into `__gl_main_cpu` (Main_CPU).  The runtime's
System.Tasking.Initialize uses it to index a small malloc'd array, and the
program dies with SIGSEGV before it prints anything.  The GNAT runtime
reports the SIGSEGV as

    raised STORAGE_ERROR : s-intman.adb:136 explicit raise

Every Ada program whose binder file triggers the same code generation is
affected, and it is deterministic.


Environment
-----------
  Target:          armv7-alpine-linux-musleabihf
  Compiler:        gcc 15.2.0 (Alpine 15.2.0), gcc-gnat 15.2.0
  libc:            musl, lazy PLT binding (the default)
  Alpine default:  CFLAGS="-Os -fstack-clash-protection -Wformat
                   -Werror=format-security"
  Program:         gprbuild (AdaCore commit 2781289e9e2b), bootstrap build
  Run under:       QEMU user-mode (qemu-arm 11.1.2), armv7 userland


Observed behaviour
------------------
  $ gprbuild --version
  raised STORAGE_ERROR : s-intman.adb:136 explicit raise

s-intman.adb:136 is the `when SIGSEGV => raise Storage_Error` arm of
Notify_Exception, so the real event is a SIGSEGV.  QEMU reports:

  --- SIGSEGV {si_signo=SIGSEGV, si_code=1 (SEGV_MAPERR), si_addr=0x42cb6814} ---
  pc = 0x408ab432  system__tasking__initialize+0x116  (libgnarl-15.so)

The faulting code is, in libgnarl:

    add.w  r3, sl, r8, lsl #2     @ r3 = cpu_array + Main_CPU*4
    ldr    r2, [r3, #4]           @ faults: Main_CPU == 0x0083f6ec

Main_CPU is expected to be -1 (the binder's default).  A watchpoint shows
the value is still -1 when __libc_start_main is entered, and is written as
0x0083f6ec by `adainit` of the executable (adainit+172).


Root cause
----------
Binder source: docs/bugs/armv7-gcc-stack-clash-miscompile/b__gprbuild.adb
(generated with `gnatbind -x gprbuild-main.ali -o b__gprbuild.adb`).

Compiled with `gcc -c -S -Os -fstack-clash-protection b__gprbuild.adb`,
the start of adainit is:

    adainit:
        @ args = 0, pretend = 0, frame = 8
        @ frame_needed = 1, uses_anonymous_args = 0
        mov     ip, #4096
        push    {r4, r5, r6, r7, r8, lr}
        sub     ip, sp, ip
        str     r0, [ip, #4064]          @ stack-clash probe
        sub     sp, sp, #8
        add     r7, sp, #0               @ r7 == sp, frame is 8 bytes
        ...
        mov     r2, #-1
        ...
        str     r2, [r7, #-8]            @ <-- 8 bytes BELOW sp
        str     r2, [r3]
        ldr     r3, .L14+16
        mov     r0, r3
        str     r3, [r7, #5]             @ unaligned store, see below
        bl      memcpy(PLT)              @ clobbers [sp-8 ..] via the PLT stub
        ...
        ldr     r2, [r7, #-8]            @ <-- reloads the clobbered slot
        ldr     r3, .L14+44
        ldr     r3, [r4, r3]
        str     r2, [r3]                 @ __gl_main_cpu := garbage

The frame is declared as 8 bytes, but the local lives at offset -8 from the
frame's lowest address.  With ARM EABI there is no red zone, and the PLT
resolver (and signal frames) may use memory below sp at any time.

A second oddity in the same prologue: `str r3, [r7, #5]` is a 4-byte store at
an odd offset that extends one byte past the 8-byte frame (offsets 5..8).

Variants of the same file (same compiler, same source):

    -Os -fstack-clash-protection   below-sp store/load: yes   <- Alpine default
    -Os                            no  (the -1 stays in r7)
    -O2 -fstack-clash-protection   no  (no sub sp / r7 frame in adainit)

So the combination of -Os and -fstack-clash-protection is needed.  The
Alpine disassembly of the installed executable shows the same instructions
(adainit at 0x27368, str.w r2,[r7,#-8] at 0x273a6, ldr.w r2,[r7,#-8] at
0x27404), so the problem is in what the compiler emits, not in the emulator.


Reproduction
------------
Inside an armv7 Alpine edge container (docker run --platform linux/arm/v7
alpine:edge, with qemu-user binfmt registered on the host):

  apk add gcc-gnat gprbuild build-base
  # get the gprbuild sources and build them (their bootstrap.sh uses $CFLAGS
  # for the Ada compiles), then:
  cd gprbuild-<commit>
  gnatbind -x gprbuild-main.ali -o b__gprbuild.adb
  gcc -c -S -Os -fstack-clash-protection b__gprbuild.adb -o bad.s
  grep -n 'r7, #-' bad.s            # shows the below-sp store and load
  gcc -c -S -Os b__gprbuild.adb -o ok.s
  grep -n 'r7, #-' ok.s             # no such access

Running the resulting gprbuild gives the STORAGE_ERROR above.

Hello-world and a one-task program do NOT trigger the code generation
(their adainit is small); a reduced test case has not been found yet.


Workaround used in the overlay
------------------------------
(Patch: gprbuild-armv7-workaround.patch in this directory.)
On armv7 only, remove -fstack-clash-protection from CFLAGS when building
Ada code (testing/gprbuild/APKBUILD, in _bootstrap()):

    [ "$CARCH" = armv7 ] && CFLAGS=$(echo "$CFLAGS" | sed 's/-fstack-clash-protection//')

-O2 instead of -Os with the protection enabled is another option.


Prior art (searched 2026-10-08)
-------------------------------
No existing report of this exact miscompile (Thumb-2, -Os, -fstack-clash-
protection, a local kept below sp across a call) was found in web searches
of GCC Bugzilla mirrors, Debian, Fedora, Gentoo and Alpine trackers and the
gcc-patches / gcc-bugs lists.  The GCC Bugzilla itself could not be fetched
(bot check), so absence there is not proven.  Related items:

  * GCC PR target/85005, "Redesign and cleanup arm.c wrt to
    flag_stack_clash_protection and flag_stack_check" (filed 2018-03-20,
    UNCONFIRMED when read).  The reporter says the ARM backend's checks vary
    from place to place, are "probably not used correctly", are untested, and
    that no Arm backend is listed in
    check_effective_target_supports_stack_clash_protection.  It describes no
    miscompile, but shows the ARM stack-clash code has been considered
    fragile.
  * Gentoo bug 675050 (2019): -fstack-clash-protection gives only "partial
    protection" on arm, and "there might be architecture-specific bugs in
    implementation of -fstack-clash-protection".
  * Red Hat's 2020 article "Stack clash mitigation in GCC, Part 3" says 32-bit
    ARM had no -fstack-clash-protection support (may be out of date).
  * Different bugs, not related: PR target/113995 (aarch64 stack-clash
    prologue ICE), an LLVM ARM frame-pointer/realignment fix (llvm-project
    PR 163699), LLVM alloca(0) with stack clash protection (Mozilla 1588710).

  Sources:
    https://gcc.gnu.org/pipermail/gcc-bugs/2018-March/618711.html
    https://bugs.gentoo.org/show_bug.cgi?id=675050
    https://developers.redhat.com/blog/2020/05/22/stack-clash-mitigation-in-gcc-part-3
    https://patchwork.sourceware.org/project/gcc/patch/mptfrxmkr2r.fsf@arm.com/
    https://github.com/llvm/llvm-project/pull/163699
    https://bugzilla.mozilla.org/show_bug.cgi?id=1588710


How it was diagnosed
--------------------
gdb cannot run the program under qemu-user (ptrace is not implemented), so
the diagnosis used QEMU's own tooling:

  * qemu-arm -L <armv7 rootfs> -d guest_errors,unimp,cpu -D trace.log -strace
    gave the signal, si_addr and the register state at the fault.
  * qemu-arm -g 1234 plus gdb-multiarch: break at __libc_start_main
    (`hbreak`), then `set can-use-hw-watchpoints 0` and
    `watch {int}<address of __gl_main_cpu>` (hardware watchpoints cannot be
    inserted); the software watchpoint stopped in adainit.
  * objdump -d of adainit and of libgnarl's System.Tasking.Initialize.


Not yet established
-------------------
  * The run was under QEMU user-mode only.  The below-sp access is in the
    generated code and does not depend on the emulator, but a run on real
    armv7 hardware has not been done.  (Whether the PLT stub's use of the
    stack below sp is what clobbers the value on real hardware was inferred
    from the corrupted value, not observed directly.)
  * armhf (armv6kz, ARM mode, not Thumb-2) crashes the same way at start-up
    (SIGSEGV turned into STORAGE_ERROR) with the default flags, and passes with
    -fstack-clash-protection removed (QEMU user-mode, 2026-10-11).  Its
    adainit does not obviously show the armv7 below-sp reload, so the exact
    mechanism there was not examined; only the flag dependence is established.
    The other architectures were not checked for the same pattern.
  * A minimal reproducer (small Ada or C source) is not available.
  * Whether this is a GCC 15 regression has not been checked (GCC 14 was not
    tried).
  * No upstream bug report has been filed, so there is no PR number.
  * Search GCC Bugzilla directly (stack-clash, arm, thumb2, wrong-code) before
    filing; the web searches above could not reach it.

Policy check (2026-10-13)
-------------------------
An earlier version of this section said GCC does not support the flag on
32-bit ARM.  That came from Red Hat's "Stack clash mitigation in GCC, part 3"
(GCC 8, 2020) and is out of date.  Checked against current sources:
  * Debian's dpkg-buildflags (dpkg 1.22+, scripts/Dpkg/Vendor/Debian.pm and
    man/dpkg-buildflags.pod) ENABLES -fstack-clash-protection by default on
    amd64, arm64, armhf and armel.
  * Fedora's redhat-rpm-config rpmrc sets it for i386..i686, x86_64, ppc64le,
    s390x and aarch64 and has no armv7hl entry (no statement of intent found).
  * A Debian ports thread (Nov 2023, seen only as a search snippet) says Arm's
    GCC maintainers confirm it is supported on 32-bit, with a different and
    buggier implementation.
So the flag is supported, and the miscompile described above is a GCC bug that
should be reported (still to do).  Meanwhile the overlay's abuild leaves the
flag out on armhf and armv7 as a workaround.

Reproduced on Debian (2026-10-13), so this is not Alpine-specific
-------------------------------------------------------------------
Debian sid, armhf (linux/arm/v7 container under QEMU), gcc-15 / gnat-15
15.3.0-4, glibc.  The same gprbuild commit (2781289e9e2b) built with
bootstrap.sh and run with `gprbuild --version`:

  flags                                                      result
  -Os -fstack-clash-protection -Wformat                      STORAGE_ERROR s-intman.adb:136
  -g -O2 -fstack-protector-strong -fstack-clash-protection   STORAGE_ERROR s-intman.adb:136
    (Debian's own dpkg-buildflags for armhf)
  -g -O2 -fstack-protector-strong   (no stack-clash flag)    works
  -Os                               (no stack-clash flag)    works

So the flag alone triggers it, at -O2 as well as -Os, with Debian's compiler and
libc: a GCC bug (target arm), not a problem of Alpine's gcc aport, musl or
abuild.  The title and summary above say -Os; correct them before filing.
Test-only change: gpr-util-put_resource_usage__unix.adb replaced by the __null
unit (GNAT 15.3 moved timeval out of GNAT.Sockets.Thin_Common).
