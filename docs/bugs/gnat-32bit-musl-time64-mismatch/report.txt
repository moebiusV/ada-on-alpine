Title
-----
[Ada] GNAT runtime on 32-bit musl (>= 1.2, 64-bit time_t): clocks are wrong and
any timed wait can spin forever; Ada imports the old 32-bit-time entry points
with a 64-bit timespec (gcc-gnat 15.2.0, i586 and armv7)

Status: not yet reported upstream.  Related upstream work exists (GCC
PR ada/114065) but it targets glibc; see "Prior art".


Summary
-------
On 32-bit Alpine (x86 and armv7, musl 1.2.6) the GNAT runtime in
gcc-gnat 15.2.0 declares its timespec with a 64-bit tv_sec, but imports
clock_gettime, clock_getres, nanosleep and pthread_cond_timedwait by their
plain C names.  On 32-bit musl those plain names are the legacy 32-bit-time
entry points (compat/time32); the 64-bit-time versions are reached only
through the headers' redirects (__REDIR(..., *_time64)), which Ada pragma
Import does not use.

The result:
  * Ada.Real_Time.Clock and Ada.Calendar.Clock return garbage;
  * delay statements measure garbage;
  * a timed wait gets an invalid timespec, pthread_cond_timedwait returns
    EINVAL, and System.Task_Primitives.Operations.Timed_Sleep spins forever
    (its `when others => pragma Assert (False)` branch is compiled out, so it
    retries with the same bad deadline).

It is timing dependent whether a program ever reaches such a wait.  Example:
`gprconfig` (part of gprbuild) hangs at exit, in
adafinal -> System.Tasking.Stages.Finalize_Global_Tasks -> Timed_Sleep.


Environment
-----------
  Alpine edge, gcc-gnat 15.2.0-r9, musl 1.2.6-r5
  x86  (i586-alpine-linux-musl), native 32-bit userland in a container
  armv7 (armv7-alpine-linux-musleabihf), under QEMU user-mode
  64-bit targets (x86_64, aarch64) are not affected (time_t is 64-bit and the
  plain names are the 64-bit functions).


Evidence
--------
1. Runtime source as installed
   (/usr/lib/gcc/i586-alpine-linux-musl/15.2.0/adainclude):
     s-parame.ads   time_t_bits : constant := Long_Long_Integer'Size;   (64)
     s-oscons.ads   SIZEOF_tv_sec : constant := 8;
     s-osinte.ads   pragma Import (C, clock_gettime, "clock_gettime");
                    pragma Import (C, clock_getres, "clock_getres");
                    pragma Import (C, pthread_cond_timedwait,
                                      "pthread_cond_timedwait");
     s-osprim.adb   pragma Import (C, nanosleep, "nanosleep");
   No time-bits constant or *64 external name exists anywhere in these files.

2. A tiny program (t64.adb in this directory) prints the
   clock, a 0.05 s delay and the calendar year.  Results, with the real
   uptime and year for comparison:

     x86     Real_Time.Clock seconds = -5589639622      (uptime 154349 s)
             delay 0.05 elapsed      = 1935114076.6 s
             Calendar year           = 2245             (real: 2026)
     armv7   Real_Time.Clock seconds = 967012111        (uptime 154363 s)
             delay 0.05 elapsed      = 4269302496.7 s
             Calendar year           = 2038             (real: 2026)

3. The hang, natively on x86 (gdb, single thread, state R, 100% CPU):

     #0 __pthread_cond_timedwait (musl, 64-bit time)
     #1 pthread_cond_timedwait (compat/time32/pthread_cond_timedwait_time32.c)
     #2 system.task_primitives.operations.monotonic.timed_sleep  (libgnarl)
     #3 system.task_primitives.operations.timed_sleep
     #4 system.tasking.stages.finalize_global_tasks
     #5 adafinal
     #6 main

   Frame #1 is the 32-bit-time wrapper, called by libgnarl.  The timespec it
   was given read as {tv_sec = -1510195928, tv_nsec = -2}; a negative tv_nsec
   makes musl return EINVAL at once.

4. Timed_Sleep (s-tpopmo.adb) retries on any result other than 0, EINTR and
   ETIMEDOUT without refreshing Check_Time:

     case Result is
        when 0 | EINTR   => Timedout := False; exit Outer;
        when ETIMEDOUT   => exit Outer when Exit_Outer;
                            Check_Time := Monotonic_Clock; exit Inner;
        when others      => pragma Assert (Standard.False);
     end case;
     exit Outer when Abs_Time <= Check_Time or else Check_Time < Base_Time;

   With EINVAL, Check_Time never changes, so the Inner loop repeats the same
   call forever.  (Finalize_Global_Tasks itself asks for only 0.01 s.)

5. Under QEMU armv7 the same wait appeared as
   futex(addr, FUTEX_WAIT, 2, {tv_sec = 814188359, ...}) and blocked for
   ~25 years; which way it fails depends on the garbage value.


Prior art
---------
  * GCC PR ada/114065, "gnat build with -D_TIME_BITS=64 -D_FILE_OFFSET_BITS=64
    fails on 32bit archs", and the patch series "ada: fix timeval timespec on
    32 bits archs with 64 bits time_t [PR114065]" (v11 in Jan 2025, up to v18
    by Jun 2025).  The series introduces a constant derived from glibc's
    __USE_TIME64_REDIRECTS / __USE_TIME_BITS64 and imports clock_get{res,time},
    gettimeofday, nanosleep, pthread_cond_{,timed}wait and select under their
    *64 names when it is set.  A reviewer asked for the "Glibc" prefix to be
    dropped because the macros must work with other C libraries such as musl;
    another participant noted GNAT needs further fixes to build on musl.
  * In that PR (comment #45, 2025-06-08), John David Anglin reports that the
    v15 patch as installed in Debian gcc-15 "causes hangs and timeouts in
    various tests": pthread_cond_timedwait in Timed_Sleep "can return EINVAL
    when the tv_nsec value in abstime is invalid. This return value isn't
    handled by Timed_Sleep and we get an infinite loop."  That is the same
    failure mechanism as here (reported on hppa-linux, glibc).
  * The merge state of the series in GCC 15/16 was not confirmed from the
    pages that could be read (the Bugzilla page itself was blocked by a bot
    check).  The installed Alpine 15.2.0 runtime has none of it.

  * Origin in Alpine (found 2026-10-12): main/gcc carries
    0034-libgnat-time_t-is-always-64-bit-on-musl-libc.patch (Soeren Tempel,
    2022-07-19), which changes time_t_bits in libgnat/s-parame.ads from
    Long_Integer'Size to Long_Long_Integer'Size.  That is right for the type
    (musl's time_t is 64-bit on every arch since 1.2.0) but leaves the runtime
    importing the plain, time32, function names, so on 32-bit Alpine it
    produces exactly this mismatch.  Before that patch the runtime used a
    32-bit timespec with the plain names and was consistent (Y2038-limited).
    The fix in this directory completes 0034; an alternative is to revert it
    on 32-bit.
  * Upstream (found 2026-10-12): GCC trunk (GCC 16), commit 41974d6ed3 by
    Nicolas Boulenguez, committed by Eric Botcazou in July 2025, "Ada: Add
    System.C_Time and GNAT.C_Time units to libgnat", PR ada/114065.  71 files:
    it moves the C time types into a new System.C_Time unit, removes
    time_t_bits from s-parame.ads, and queries sizes from s-oscons-tmplt.c.
    From the commit page it does not mention musl or the _time64 symbols; that
    was not established.  It is on trunk, not in the 15.x release Alpine ships.
    A patch for upstream would have to be rebased onto System.C_Time.
  * The GCC Bugzilla is still behind a bot check (Anubis), so the PR's own
    status was not read.

  Sources:
    https://www.mail-archive.com/gcc-bugs@gcc.gnu.org/msg866766.html
    https://gcc.gnu.org/pipermail/gcc-patches/2025-January/672546.html
    https://gcc.gnu.org/bugzilla/show_bug.cgi?id=114065
    https://bugzilla-archive.dlang.org/bugs/23608/   (the same musl >= 1.2
        32-bit linking pitfall in the D runtime: time functions linked to the
        32-bit symbols give wrong results)


Patch and test results
----------------------
gnat-musl-time64.patch (this directory; against gcc 15.2.0, gcc/ada/) makes
the following changes, 11 hunks in 6 files:
  * s-linux.ads: timespec/timeval get a sub-second field as wide as time_t, so
    the Ada record is 16 bytes like the C one on 32-bit targets with a 64-bit
    time_t (little endian only).
  * s-osinte.ads/.adb, s-osprim.adb, a-exetim.adb: a Time64 constant (32-bit
    address and 64-bit time_t) selects the musl time64 entry points:
    __clock_gettime64, __clock_getres_time64, __nanosleep_time64,
    __gettimeofday_time64, __pthread_cond_timedwait_time64.
  * s-osprim.adb, g-calend.ads: the timeval buffers are 16 bytes.
  64-bit targets keep the plain names and are unchanged.

Tested on x86 (native 32-bit, musl 1.2.6) with a private copy of the runtime
(`gnatmake --RTS=<copy> -a -gnatpg -gnatn -O2 -fPIC`, linked -static):
  t64.adb:  Real_Time.Clock seconds = 155500 (= uptime), 0.05 s delay measured
            0.0502 s, Calendar year 2026.
  gprbuild: bootstrapped from source against the patched runtime; the
            previously hanging `gprconfig --batch --target=x86-linux
            --fallback-targets --config=ada,,,,` completes (20 runs in 4 s;
            the unpatched binary timed out in 2 of 3 runs), and the patched
            gprbuild builds and runs a hello program in about 1 s.
  armv7:    test in progress when this was written; see the status below.

Fix for the main/gcc MR (v2, 2026-10-12)
----------------------------------------
0044-ada-use-the-time64-functions-on-32-bit-targets-with-a-64-bit-time_t.patch
(git-format style; applies cleanly to GCC 15.2.0 plus Alpine's Ada patches
0015, 0026, 0027, 0028, 0034, 0040, 0041, 16 hunks in 9 files) replaces the
flat-runtime patch (kept as gnat-musl-time64-flat-runtime.patch, which is what
the gprbuild aport uses for its private runtime).

Design: the Ada runtime must not assume the C types; the C compiler says what
the target does.
  * s-oscons-tmplt.c now reports SIZEOF_timespec, SIZEOF_tv_nsec,
    OFFSET_tv_nsec and TIME64_REDIRECTED (the C library redirects its plain
    time functions to time64 variants and long is narrower than time_t:
    musl on 32-bit targets, glibc built with _TIME_BITS=64).
  * adaint.c has six thin __gnat_ wrappers (clock_gettime, clock_getres,
    nanosleep, gettimeofday, pthread_cond_timedwait, select), compiled against
    the same headers, so they reach whichever function the headers bind to.
    They exist only when TIME64_REDIRECTED would be 1.
  * s-osinte__linux.ads, a-exetim__posix.adb, s-osprim__posix.adb and
    g-socthi.ads import the wrappers when TIME64_REDIRECTED is 1 and the plain
    names otherwise.
  * time_t, suseconds_t and timespec (System.Linux, System.OS_Primitives,
    GNAT.Sockets.Thin_Common) take their widths from System.OS_Constants, and
    timespec gets the C size and tv_nsec offset: on 32-bit musl it is 16 bytes
    and the kernel writes all of it, so a 12-byte Ada record overflowed.
  Nothing changes where TIME64_REDIRECTED is 0: every 64-bit target and 32-bit
  glibc by default.  glibc built with _TIME_BITS=64 is covered by
  __USE_TIME_BITS64 but NOT tested (no 32-bit glibc here).

0045-ada-enable-Ada.Execution_Time-on-arm-riscv-and-s390-linux.patch is a
separate, two-line-per-block Makefile.rtl change: the POSIX Ada.Execution_Time
was selected for x86, x86-64, x32, ia64, PowerPC, AArch64 and LoongArch Linux
but not ARM, RISC-V or S/390, where any use failed with "Execution_Time is not
supported in this configuration".  No bug report for that gap was found.

Tests (t64.adb: clock/delay/calendar; t64b.adb: adds a timed entry call,
Ada.Execution_Time and a GNAT.Sockets select timeout; t64c.adb: t64b without
Execution_Time; test-one-arch.sh runs them in an Alpine container).  Each
arch's s-oscons.ads was regenerated with GNAT's own xoscons from the patched
template, and the runtime was a private copy of the installed one with the
patched units recompiled (gnatmake -a), the wrappers linked in.  All on Alpine
edge, gcc-gnat 15.2.0-r9, musl 1.2.6, natively (x86, x86_64) or under QEMU:

  arch         TIME64  control (unpatched)         patched
  x86          1       garbage clock, year 2310,   all pass (clock = uptime,
                       timed entry call hangs      delay 0.050, timed entry
                                                   call 0.300, select 0.300)
  armv7        1       clock -2800018356 s,        all pass, incl. Execution_Time
                       year 2256                   (with 0045)
  armhf        1       (same bug)                  all pass, incl. Execution_Time
  x86_64       0       correct                     all pass, unchanged
  aarch64      0       correct                     all pass, unchanged
  ppc64le      0       correct                     all pass, unchanged
  s390x        0       correct                     all pass; Execution_Time (0045)
  riscv64      0       correct                     all pass; Execution_Time (0045)
  loongarch64  0       correct                     all pass, unchanged

glibc (checked 2026-10-12 on arm32v7/debian:trixie-slim under QEMU, glibc 2.41,
gnat-14 14.2.0-19, container armv7-debian-dev):
  * Debian's armhf toolchain binds the C time functions to the 64-bit variants
    by default (nm of the wrappers shows __clock_gettime64, __clock_getres64,
    __nanosleep64, __gettimeofday64, __pthread_cond_timedwait64, __select64).
  * GNAT's real xoscons pipeline on the patched template gives SIZEOF_tv_sec 8,
    SIZEOF_tv_usec 8, SIZEOF_timespec 16, SIZEOF_tv_nsec 4, OFFSET_tv_nsec 8 and
    TIME64_REDIRECTED 1 both by default and with -D_TIME_BITS=64
    -D_FILE_OFFSET_BITS=64: the same as musl, so the __USE_TIME_BITS64 branch of
    the condition works.
  * Debian's runtime (GCC 14 with the PR 114065 series backported, System.C_Time)
    imports glibc-specific names chosen by OS_Constants.Glibc_Use_Time_Bits64
    (__clock_gettime64, __clock_getres64, __nanosleep64, __gettimeofday64,
    __pthread_cond_timedwait64).  Clocks, delays and timed entry calls are
    right there.  But GNAT.Sockets still imports the plain "select": on armhf
    Check_Selector with a 0.3 s timeout returns EXPIRED after 0.0008 s (the
    legacy select reads the 64-bit timeval as a zero timeout).  Importing
    __gnat_select (our wrapper, compiled against glibc's headers, so it calls
    __select64) fixes it: 0.301 s.  So the wrapper approach is libc-neutral and
    covers select, which the glibc-specific names missed.
  * Not done on glibc: applying the whole patch (it is made against GCC
    15.2.0, Debian's runtime is 14.2 with the C_Time rework).

Full gcc build (2026-10-12, x86, native 32-bit musl, Alpine's gcc aport 15.2.0-r10
with 0044 and 0045 added to source=, languages c,c++,ada, --disable-bootstrap,
4 CPUs): builds in 10 minutes and produces the 13 normal packages.  The first
attempt failed in the Ada runtime build: GCC builds the runtime with warnings as
errors and GNAT said 's-osprim.adb:56:28: warning: 32 bits of "timespec"
unused' (the 4 bytes of C padding); the earlier private-runtime tests had used
-gnatws and missed it.  Fixed with a scoped pragma Warnings in s-osprim__posix.adb
and s-linux.ads.  With the packages installed, the stock gnatmake and no
private runtime: t64, t64b (incl. Execution_Time) and t64c all pass (clock =
uptime, delay 0.050, timed entry call 0.300, select 0.300), and libgnat-15.so
exports __gnat_clock_gettime, __gnat_nanosleep and __gnat_select.

Still not done: a full gcc-gnat build on the other architectures (only the runtime units were
rebuilt privately); testing on glibc.  GNAT.Sockets' other users of timeval
(setsockopt timeouts) go through OS_Constants-sized types and were not
exercised.

Possible fixes (for discussion)
-------------------------------
  * In the Alpine gcc aport (main/gcc, not this overlay): patch the Ada runtime
    so that, on musl 32-bit, the imports use the musl time64 symbols
    (exported by ld-musl-i386.so.1 in musl 1.2.6: __clock_gettime64,
    __clock_getres_time64, __nanosleep_time64, __clock_nanosleep_time64,
    __pthread_cond_timedwait_time64), or declare the timespec with the 32-bit
    layout.
  * Independently, Timed_Sleep should not spin on EINVAL.


Not yet established
-------------------
  * gnat-musl-time64.patch was made against the INSTALLED runtime sources, which
    are flat (gcc/ada/s-linux.ads).  In the GCC 15.2.0 source tree they are
    under gcc/ada/libgnat/ and gcc/ada/libgnarl/, and the Linux files carry
    target suffixes (s-osinte__linux.ads, s-osprim__posix.adb,
    a-exetim__posix.adb), so the patch does not apply to Alpine's main/gcc
    as it stands and must be remade against the source tree.
  * (Checked: the musl time64 symbol names listed above exist in
    ld-musl-i386.so.1 of musl 1.2.6; the armv7 library was not inspected.)
  * The armv7 hang was seen only under QEMU; the wrong clock was seen on both.
  * Whether the PR114065 series, once complete, would cover musl is unknown.
  * No upstream report has been filed for the musl case.
