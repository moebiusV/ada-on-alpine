Title
-----
[vss-text] VSS.Implementation.UCD_Utilities.Extract_Core_Data reads wrong
Unicode properties on big-endian targets (s390x): Display_Width of "(" is 2

Status: not yet reported upstream (AdaCore/vss-text).  Patch: ucd-endianness.patch.


Summary
-------
VSS.Implementation.UCD_Core stores the core character properties as 32-bit
words (Core_Data_Raw_Table), fields at fixed bit positions counting from the
least significant bit.  It then overlays an array of Core_Data_Record on that
table, a packed record whose fields are placed with "at 0 range N .. M".  Such
a layout follows the bit and byte order of the machine, so the overlay reads
the right fields only on little-endian targets.

On s390x (big-endian) the properties are decoded wrongly.  Seen: Display_Width
of "(", ")", "[", "]" and "{" is 2 instead of 1.


Effect downstream
-----------------
Prettier_Ada lays text out by display width, so lines holding a bracket pair,
a parenthesis pair or a call broke two columns early.  That failed three
Liblktlang unparsing tests of the langkit testsuite on s390x only:
unparsing/array_lit, unparsing/dot_expr, unparsing/raise_expr.


Fix
---
Decode the raw word with shifts and masks in Extract_Core_Data, the only user
of the table.  The result is the same on every machine; on little-endian
targets it is unchanged.  Field positions are those of Core_Data_Record
(GC 0..4, flags at 5, 6, 7, GCB 8..11, InCB 12..13, ExtPict 14, WB 16..20,
EA 24..26, Emoji 27, EBase 28, EMod 29, EPres 30).

Checked:
  * s390x, patched libvss-text.so against langkit's lkt testsuite: the three
    tests pass (full lkt suite 114 pass, 0 fail, 2 skipped; unpatched VSS:
    110 pass, 4 fail).
  * the s390x CI job of the Alpine overlay passes the langkit testsuite with
    the patch.
Not checked: other big-endian targets (ppc64 big-endian, etc.).  Not
benchmarked; the decode is a few shifts per lookup.


Suggested upstream form
-----------------------
The patch is minimal.  A cleaner change may be to generate the table with the
packed fields already combined, or to add a big-endian representation clause
(for Core_Data_Record'Bit_Order use System.High_Order_First with swapped
positions); the shift-and-mask version was chosen because it needs no
generator change and cannot depend on the machine's bit order.


Second report: the casing and normalization tables (same mistake)
------------------------------------------------------------------
Patch: ucd-mapping-endianness.patch.

VSS.Implementation.UCD_Casing_UTF8 (Simplified_Mapping_Data_Table,
Contextual_Mapping_Data_Table) and UCD_Normalization_UTF8 (Mapping_Data_Table)
overlay a record on a table of raw 32/64-bit words in the same way, and read
wrongly on big-endian targets.

Found through ada_language_server, whose "--version" check died on s390x with
    CONSTRAINT_ERROR : vss-implementation-utf8_strings-mutable_operations.adb:700
    range check failed
A stack trace taken with QEMU's gdb stub (qemu-user, gdb inside an s390x
container) gave: lsp-ada_configurations elaboration (line 43) lower-cases a
string -> VSS.Strings.Transform -> vss.transformers.casing.transform ->
convert_case -> convert_case_full -> Unchecked_Append with from => 18562 (a
garbage offset into UTF8_Data_Table) -> range check.

Test (13 cases through the VSS.Transformers.Casing and .Normalization objects:
ASCII and accented lower/upper case, Greek final sigma, sharp s, NFC/NFD/NFKC/
NFKD of an accented letter, a ligature and Hangul): on s390x 12 failed (three
with the Constraint_Error above, one Program_Error and one Constraint_Error
"invalid data" in the normalization); with the patch all pass.  Then
ada_language_server built and passed its check on s390x.

Fix: decode the raw word with shifts and masks in Get_Contextual_Case_
Mapping_Information, Get_Simplified_Case_Mapping_Information and Get_
Decomposition_Information; unchanged on little-endian.  Not checked: other
big-endian targets; the little-endian result was not re-run (the decode follows
the bit positions of the existing representation clauses).
